# Audit du VPS Render — fonctionnalités, langage naturel et répondeur

Date de l'audit : 25 septembre 2026. Périmètre : application déployée sur Render et code de ce dépôt qui la construit. Aucun VPS R1, PC local ou téléphone n'a été inspecté.

## Compte de vérification

Compte de test unique pour les essais d'intégration Render : `KEY-B4403774-2026`, documenté comme règle projet dans [TESTS-REELS.md](TESTS-REELS.md). Le contrôle Render confirme, pour ce compte, une session WhatsApp connectée/appariée et une session Telegram connectée/appariée; les deux canaux sont activés. Les numéros personnels et secrets API ne sont pas consignés.

## Résumé de l'inspection du code

- `index.js` contient **212 déclarations de routes HTTP** qui couvrent les interfaces, contrôles de compte et moteurs Render décrits ci-dessous.
- Le registre central contient maintenant **147 tools** : 107 outils historiques, 28 tools Render, 4 tools de mission, 4 tools de statut/déconnexion et 4 tools de connexion/appairage. Ces derniers sont dans les modules `objective-missions.js`, `channel-sessions.js` et `channel-login.js`; les outils historiques gardent leur moteur existant.
- Chat intelligent et self-chat WhatsApp/Telegram convergent vers `chatOrchestrator.handle` et le même `toolRegistry`/`agentLoop`. Les tests vérifient la découverte d'un module ajouté sans modifier ces trois interfaces.
- Un registre commun ne signifie pas que les 212 routes disposent toutes déjà d'un tool. Les lacunes concrètes sont listées dans « Couverture et limites »; cet audit ne les déclare pas pilotables.

## Chemin d'exécution vérifié dans le code

`Chat/self WhatsApp/self Telegram → chatOrchestrator.handle → agentLoop ou missionOrchestrator → toolRegistry.execute → moteur existant → vérification du résultat → réponse`. Pour un objectif multi-étapes, l'IA planifie et peut replanifier après une lecture réelle; les opérations déterministes du plan ne redemandent pas un appel IA à chaque étape. Les trois interfaces utilisent le même routeur. Les nouveaux modules de `ai-engine/tool-modules/` sont découverts au démarrage sans changement des routeurs.

## Répondeur : chaîne et résultat de l'audit

Le traitement entrant réel est orchestré par `index.js` et `assistantLayer`; selon identité, canal, groupe et réglages, il route vers le canal du propriétaire, l'assistant conversationnel ou `autoResponder`. Le répondeur construit identité/contexte métier et conversation, applique les règles (STOP/refus, doublons, opt-out, groupe, activité humaine), demande une rédaction IA si nécessaire, puis appelle l'adaptateur d'envoi vérifié. Les défauts certains corrigés dans cette branche étaient l'identifiant consommé avant validation du runtime et la confusion entre `PENDING` et envoi confirmé. Un statut `PENDING` ne vaut plus preuve de livraison; l'envoi direct ne marque une réponse confirmée qu'avec `SUCCESS` et un `confirmationId`. Les erreurs certaines d'envoi peuvent être retentées. Le chemin de closing qui remet le brouillon à son appelant est explicitement marqué comme livraison différée.

Limite de preuve : les tests disponibles utilisent runtime/LLM contrôlés. Ils ne prouvent ni réception d'un vrai message WhatsApp/Telegram externe sur Render ni remise effective d'une réponse automatique à ce client. La route de diagnostic synthétique ne remplace pas cette preuve. Le répondeur ne peut donc pas être déclaré « réparé de bout en bout » avant cet essai live.
